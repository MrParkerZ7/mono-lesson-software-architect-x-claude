## 5.1 Role Overview

The **Domain Architect** specializes in architecture for a specific business domain such as payments, healthcare, supply chain, or trading. They bring deep domain expertise combined with technical skills to design solutions that address domain-specific requirements, regulations, and patterns.

## 15.8 Sample Scenarios

### Scenario 1: Payments Modernization

**Situation**: A bank needs to modernize their legacy payments infrastructure to support real-time payments and open banking.

**Domain Architect Actions**:
1. Map current payment capabilities and gaps
2. Define target state architecture aligned with ISO 20022
3. Design real-time payment processing capability
4. Create open banking API strategy (PSD2 compliant)
5. Plan legacy system integration and migration
6. Address regulatory requirements (PCI, KYC/AML)
7. Define fraud detection integration
8. Create phased implementation roadmap

### Scenario 2: Healthcare Interoperability

**Situation**: Health system needs to share patient data across multiple facilities and with external partners.

**Domain Architect Actions**:
1. Assess current data formats and systems
2. Design FHIR-based interoperability layer
3. Create patient consent management architecture
4. Define security and audit requirements (HIPAA)
5. Design integration with external health networks
6. Plan migration from HL7 v2 to FHIR
7. Create data governance framework
8. Establish interoperability testing strategy

## 15.9 Comparison with Other Roles

| Aspect | Domain Architect | Solution Architect | Enterprise Architect |
|--------|-----------------|-------------------|---------------------|
| **Focus** | Specific business domain | Project solutions | Enterprise-wide |
| **Domain Depth** | Expert | Varies | Broad |
| **Regulatory** | Deep expertise | Basic awareness | Policy level |
| **Scope** | Domain-wide | Project | Organization |
| **Business Knowledge** | Expert | Good | Strategic |

## Key Takeaways

- Domain Architects combine **deep domain expertise with technical skills**
- **Regulatory compliance** is often a critical concern
- Must speak **both business and technical language** fluently
- **Industry standards** knowledge is essential
- **Domain-Driven Design** provides valuable patterns
- Success requires **building credibility** in the domain

## Practical Exercises

1. **Domain Modeling**: Create a domain model for an e-commerce order fulfillment system including bounded contexts.

2. **Compliance Mapping**: Map PCI DSS requirements to technical controls for a payment processing system.

3. **Capability Map**: Create a capability map for a domain of your choice (healthcare, retail, etc.).

4. **Integration Design**: Design a healthcare data exchange using FHIR resources.
